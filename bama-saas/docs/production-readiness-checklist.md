## Product (one sentence)

A personal used-car deal finder: crawl bama.ir, quote a fair price against a
cohort, surface underpriced listings, show where the market is moving, and tell
a signed-in buyer when a followed car shows up cheap.

## Stack and deploy

- Django 5.2 + DRF, PostgreSQL 16, Redis (cache only), React 19 + Vite, gunicorn,
  nginx, compose worker loop (`flock`, no Celery).
- Local: `docker-compose.yml`. Production: `docker-compose.prod.yml` behind Caddy
  on a VPS. CI on every push; deploy to `main` after CI, SSH-forced to one script.
- Hardened profile is the default (`DJANGO_DEBUG` unset). Login required in prod.

## Findings (2026-09-09 pass)

1. **The auth throttles were bypassable with a header.** DRF buckets a throttle
   on `get_ident`, and with `NUM_PROXIES` unset that is the *whole*
   `X-Forwarded-For` string. Caddy and nginx both append rather than replace, so
   the caller's own value stays in it — one guess per header value. Measured: 25
   wrong passwords with a rotating header, 25 × 401 and not one 429; the same 25
   without the header, 15 × 429. Login, register and password-change were all
   open, and each guess costs the server a PBKDF2. Fixed with `NUM_PROXIES = 2`
   (the deployed chain), pinned by
   `test_login_throttle_cannot_be_reset_by_a_forwarded_for_header`.
2. **The followed-car digest cost a query per followed car.** Measured at 15
   followed scopes: 17 queries, none cached, on every load of Saved. Brand and
   model scopes now read through `research.read_indexes` — one query per scope
   *kind* — and the trim/model-year scopes go through a cached
   `views.movement_payload`. Same 15 scopes now cost 8, and the model-scope half
   is constant in the number followed (pinned by a query-budget test).
   `movement_payload` deliberately does **not** reuse `movement_view`'s
   `cached_answer`: that pairs the answer with a fresh `_coverage()` read, which
   turned each followed trim from one query into three, and the digest prints no
   coverage block to justify it.
3. **`/saved` overflowed a phone viewport by 46 px.** Measured at 390 px:
   `scrollWidth` 436 against `clientWidth` 390, which also dragged the fixed
   bottom nav off-screen. Cause: `.card` carried `min-width: auto`, so a card
   wrapping a table grew to the table's min-content width instead of letting
   `.table-wrap` scroll — `minmax(0, 1fr)` on `.stack` clamps the *track*, not
   the item. A screenshot could not show this (see the RTL note below); the fix
   is `min-width: 0` on `.card`, re-measured as fitting at 390/768/1440.
4. **The image proxy trusted redirects.** `is_cdn_url` guarded the URL asked
   for, not the one answered, and `requests` follows redirects — so a 302 off the
   CDN would hand an unauthenticated, deliberately unthrottled endpoint's reader
   whatever it landed on, which from inside the compose network is Postgres,
   Redis or the metadata address. Now the final `response.url` is re-checked.
5. **The prod image resolved dependencies differently from CI.**
   `Dockerfile.prod` carried `npm ci --legacy-peer-deps` for a conflict between
   `openapi-typescript` and a pinned TypeScript. Neither package nor conflict is
   in the lockfile any more; CI has been running plain `npm ci` all along. The
   flag's only remaining effect was to let the shipped image differ from the tree
   CI type-checked.
6. **13 Radix packages were declared and never imported.** Every Radix import
   goes through the `radix-ui` umbrella; the individual `@radix-ui/react-*` deps
   were dead, and their presence invites the deep-import mistake that already
   took the app down once (React error #130). Removed; `npm ci` still resolves
   162 packages, so nothing shipped changed.
7. **A dev server on a moved port broke every POST, confusingly.** Django checks
   `Origin` against the request's own host (and `CSRF_TRUSTED_ORIGINS`, whose
   default names 5173/5174); Vite silently auto-increments off a busy port, and
   `changeOrigin: true` rewrote Host but not Origin, so the two could not match.
   Reproduced on 5199: all reads 200, `POST /api/alerts/mark-read/` 403 "Origin
   checking failed" — which reads as a session bug and is three screens from its
   cause. Fixed by `changeOrigin: false` in `vite.config.ts` (with
   `scripts/vite-proxy.test.ts` pinning that Host *and* Origin survive the
   proxy). `strictPort: true` is belt-and-braces on top: the port is named in
   this file, `VITE_API_TARGET` and the backend `.env`, and a silent slide
   desynchronises all three. `.env.example` now documents the pairing.
8. **`.env.example` still claimed the first account becomes staff.** The README
   was corrected last pass; this file was not.
9. **`NUM_PROXIES` was a constant nobody could check.** Fixing finding 1 replaced
   a bypass with a hop count that fails badly in *both* directions and could only
   be confirmed by reasoning about the deployment. `/api/admin/health/` now
   reports the received chain and the `resolved_ident` DRF will bucket on, read
   straight out of `BaseThrottle.get_ident` so it cannot drift from the throttle
   it describes. Two tests pin it — the correct chain, and the too-low case that
   silently returns the proxy's address.
10. **The price-drops panel mangled titles on a phone.** Five columns at 390 px
    wrapped «پژو ۲۰۶ تیپ ۲ مدل ۱۴۰۱» to one word per line and clipped the date to
    `/۱۵`. Two columns give way below 560 px, chosen on different grounds: the
    previous price *goes* (current price and the fall restate it), the date
    *moves* under the title (nothing else says when). No fact is lost at either
    width, and only one copy of the date is ever in the accessibility tree.

## Findings (2026-09-08 pass)

1. **Followed scopes had no digest.** Users can follow a brand/model/trim, but
   Saved only listed favourite *ads*. The product audit named this as the last
   Q2 frontend gap. Closed with `GET /api/watchlists/digest/` and a panel on Saved.
2. **No password change.** Logout-everywhere existed; changing a password did
   not. There is still no email-based *forgot* password (no mail backend).
   Operator reset is Django admin.
3. **Users were absent from Django admin.** Staff could not deactivate an
   account or set a password without a shell.
4. **README claimed the first signup becomes staff.** Code and tests refuse
   that; staff is `createsuperuser` only. Docs were lying.
5. **RESTORE.md claimed there is no prod compose file.** There is
   `docker-compose.prod.yml`. The restore steps still apply; the preface was wrong.
6. **`.env.production.example` was missing** despite being allow-listed in
   `.gitignore`. Operators had only compose `:?` errors as documentation.
7. **Alert rules ignored the model.** A cheap car on the `ml` board could not
   be the thing a rule asked for. Closed with optional `min_residual_pct`.
8. **Production compose never passed `CSRF_TRUSTED_ORIGINS`.** Settings fell
   back to localhost, so HTTPS session POSTs could 403. Now required (`:?`).
9. **pip-audit:** Django 5.2.16 (GIS DoS — we do not load GeoDjango), DRF 3.17.1
   (request-size bypass; AdminRenderer leak we do not use). Floors raised.
   sqlparse ReDoS is transitive; we do not format user SQL. setuptools/pip are
   venv tooling. **npm audit --omit=dev:** 0 vulnerabilities.

## Decisions

- Password change keeps the current session (`update_session_auth_hash`) and
  blacklists JWT refresh tokens. Other browser sessions die because Django
  stores a password-derived session hash. Logout-everywhere remains the
  explicit “all devices” button.
- Forgot-password via email is **not** built: no `EMAIL_*` settings, and
  sending mail from this VPS is a product/ops choice (cost, deliverability).
  Operator reset via admin is the path until that is decided.
- Watchlist digest reuses stored brand/model index series and on-demand
  `_movement` for trim/year — same numbers as Analyse, no new pipeline step.
- A residual bar is additive, not a replacement: cohort discount and peer
  floor still apply. DATA-anomaly predictions never match, same as `band=ml`.
- No payments in this product.
- Next deploy **must** have `CSRF_TRUSTED_ORIGINS` in `.env.production` or
  compose will refuse to start. The example file already lists it.

### Restore rehearsal, 2026-09-09

Docker is not available on this machine, so the compose form in
[`RESTORE.md`](../deploy/RESTORE.md) could not be run verbatim. What *was* run is
the same command chain with `docker compose exec -T postgres` replaced by the
local binaries — which exercises every part that can actually be wrong (the
crypto parameters, the archive format, the `pg_restore` flags, the verification
queries). Source database: the real migrated schema, 39 tables, seeded.

| Step | Result |
| --- | --- |
| `pg_dump --format=custom --no-owner --no-acl` → `openssl enc -aes-256-cbc -salt -pbkdf2 -iter 310000` | 164 KB archive |
| Script check 1 — full decrypt to `/dev/null` | clean end to end |
| Script check 2 — TOC listing | 39 tables with data, `accounts_user` present |
| Wrong passphrase | **refused** (does not silently yield garbage) |
| `openssl enc -d` → `pg_restore --exit-on-error --no-owner --no-acl` | exit 0 |
| Row counts, source vs restored | users 7/7, models 4/4, migrations 74/74, tables 39/39 |
| Schema objects, source vs restored | indexes 226/226, FKs 48/48, unique 74/74, check 5/5 |
| `manage.py check` on the restored copy | no issues |
| `manage.py migrate --check` on the restored copy | schema matches the models |
| A real credential against a restored row | `authenticate()` succeeds |

Both scratch databases were dropped afterwards.

**Correcting an earlier overstatement in this document:** "the VPS's archive and
live passphrase are unproven" was too pessimistic. `backup_postgres.sh` decrypts
the real archive with the real `BACKUP_PASSPHRASE_FILE` end to end *every night*,
lists its TOC, renames the file `.rejected` if either fails and sends a Telegram
alert — so passphrase-and-file decryptability is continuously verified on the
VPS, not merely assumed. `check_backup_freshness` covers the one thing the script
cannot see (the cron never firing), because it watches the artifact's age rather
than the job.

The residual gap is narrower and already named in the script's own comments: CBC
is malleable, so a single flipped byte mid-file decrypts clean and would only
surface on a real restore; the `.sha256` written alongside guards bit-rot after
the fact. Closing it means a nightly restore into a scratch database — the
rehearsal above is exactly that procedure, proven correct. It is **not** wired
into the nightly job on purpose: the production database is ~2.4 GB and the VPS
runs three stacks, so doubling it nightly is a disk-pressure decision for the
operator, not a default worth imposing from here.

### Measuring, not screenshotting

Measure, do not screenshot, on this app: it is RTL, so overflow lands at a
*negative* left and a headless capture of the wrong scroll slice looks identical
whether the page is broken or fine. `documentElement.scrollWidth` vs
`clientWidth` is the signal; bisect by hiding subtrees to find the contributor.
The picture is still worth taking afterwards — it is what showed the car names
wrapping one word per line once the overflow was gone.

## Blockers (need user / environment)

- **Forgot password over email** needs an SMTP (or equivalent) decision and
  secrets. Not implemented.
- **Production mail / monitoring SaaS** not in repo; health is compose probes +
  logs.
- **Live production traffic / backup freshness** cannot be asserted from this
  workspace without the VPS.
- **Next deploy:** set `CSRF_TRUSTED_ORIGINS` in VPS `.env.production` (example
  already has the public URL) or compose interpolation fails.
- Image rebuild needed to pick up Django 5.2.17 / DRF 3.17.2 floors.
- **Confirm the proxy chain on the next deploy — one request, no reasoning.**
  `NUM_PROXIES = 2` assumes Caddy → nginx → gunicorn, each appending one
  `X-Forwarded-For` entry. Too low buckets every visitor together (one attacker
  locks everybody out); too high hands the throttle key back to the caller.
  `GET /api/admin/health/` (staff) now returns a `forwarding` block carrying the
  received chain, `REMOTE_ADDR`, the configured count, and — via DRF's own
  `BaseThrottle.get_ident` rather than a second copy of the arithmetic — the
  `resolved_ident` the login throttle will really bucket on. Open it from a
  machine whose public address you know:
    - `resolved_ident` **is that address** → correct.
    - it is a container/private address (`172.x`, `10.x`) → count too low.
    - it echoes a value you can inject → too high.

  Pinned in both directions by `test_health_reports_the_address_the_throttles_will_bucket_on`
  and its too-low sibling, so the diagnostic cannot rot into something plausible.
- Do not push, do not edit `.env`, do not mutate production.

## Intentional deferrals

- **`AlertDelivery` history is loaded whole every hot tick.** `deliver_alerts`
  reads every delivery ever made for the users with enabled rules to build its
  "already sent" set. Correctness does not depend on it (the unique `(user, ad)`
  constraint is the real guard) and the table is days old, so the denominator
  does not justify a change yet. Bound it to ads still on the board if the table
  gets large.
- **The echarts chunk is 557 KB / 189 KB gzipped.** Already modular
  (`echarts/core` + line/bar + canvas only) and lazily imported by the two pages
  that draw, so it is off the initial payload. Nothing cheap left.
